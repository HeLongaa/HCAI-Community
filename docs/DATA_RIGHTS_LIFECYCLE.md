# Data Rights Lifecycle

LEGAL-02 implements the personal-account data export and account deletion lifecycle. Requests require a session issued within 15 minutes, exact handle confirmation, and the current account version. A subject is persisted only as a one-way `subject_` hash in operational evidence.

## Owner Flow

`POST /api/users/me/data-rights/requests` creates either `data_export` or `account_deletion`. Owners can list and read only their own requests. Eligible requests can be cancelled with their current request version. No more than three requests may be created in a rolling 30-day window, and duplicate active requests of the same type are rejected.

An export is generated by an authorized operator, is capped at 5 MiB, expires after seven days, and yields a private download valid for exactly 15 minutes. The package covers account, profile, task, community, library, media, generation, decrypted Chat, notification, support, and billing data. Credential, token, secret, ciphertext, raw payload, cookie, authorization, and network-hash fields are recursively removed.

## Deletion Flow

Account deletion has a 30-day cancellation window. Primary processing revokes identity, sessions, developer credentials, and webhooks; deletes Chat and notifications; marks media for object cleanup; anonymizes profile, creative, community, and task content; and retains only minimum support, billing, audit, and safety facts. The transaction emits one immutable receipt for each of 15 declared domains.

External Provider deletion completes before local primary deletion and stores only bounded hash evidence. Every external generation must have at least one Provider job or request reference; an unresolved generation blocks local deletion. The version 2 gateway request sends sorted, unique operation references in deterministic batches of at most 100, with a distinct idempotency key and SHA-256 for each batch. A successful processor receipt must echo the request id, Provider id, batch index/count, operation-reference hash, and exact processed-reference count. Mismatched, legacy, partial, or zero-work receipts fail closed. The application aggregates all bound batch receipts before local deletion, so references beyond the first 100 cannot be silently skipped. Successful external deletion uses the constrained `externally_erased` receipt disposition; migration `0101` aligns the PostgreSQL constraint with that runtime contract.

The currently deployed HCAI Router exposes account deletion and time-bounded log cleanup, but no request-scoped erasure endpoint. Neither operation satisfies this gateway contract for a shared Router account. Production therefore requires a separate reviewed processor that can erase every supplied operation reference and return the bound version 2 receipt; configuring the Router account-delete or log-cleanup route as the gateway is prohibited.

Primary deletion changes the request to `primary_completed`. Final completion requires immutable expiry receipts for `primary_database`, `object_storage`, and `audit_archive`, each recorded no earlier than 35 days after primary completion. Ordinary updates and deletes on event, export, deletion, and backup evidence tables are rejected by PostgreSQL triggers. Maintenance cleanup requires the explicit transaction-local setting `app.data_rights_maintenance=on`.

## Operations

The Admin Users workspace exposes queue filters, aggregate active/completed/overdue metrics, request processing, and backup evidence entry. `admin:data-rights:read` grants queue access; `admin:data-rights:manage` grants primary processing and backup receipt creation. Every Admin mutation is domain audited and uses optimistic request versions.

`admin:data-rights:legal-hold` controls the scoped legal-hold registry. Each hold names exactly one deletion domain, stores only a SHA-256 authority reference, requires review within 90 days, expires within 365 days, and has append-only creation/release events. Active holds preserve only their named domains while unrelated domains continue through deletion. The request remains `blocked`; release or natural expiry lets the bounded deletion Worker resume the same request and create only the missing domain receipts.

Legal-hold creation and the account-deletion cutoff share a subject-scoped PostgreSQL transaction lock. Once deletion is `processing`, Provider dispatch is uncertain, or the requested domain already has a receipt, hold creation fails with `DATA_RIGHTS_LEGAL_HOLD_CUTOFF_PASSED`; a hold that commits first remains authoritative for its domain.

The deletion Worker retries `identity_verified` and `blocked` requests when due. It also recovers `processing` requests only after `DATA_RIGHTS_DELETION_PROCESSING_RECOVERY_SECONDS` (300 seconds by default), preventing immediate overlap while allowing a process crash after the durable cutoff to resume with the same Provider idempotency key.

Do not mark production backup expiry complete from fixture or local evidence. The isolated RELEASE-01 runner now verifies backup-object deletion and restore-negative HEAD/GET behavior after a simulated 35-day boundary. Production acceptance still requires an actual backup inventory, real lifecycle scheduling, managed-key destruction, protected target-environment execution, and retained audit evidence. The governance status deliberately records local rehearsal implementation while `backupDeletionRehearsed` remains false.

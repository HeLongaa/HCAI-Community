# HCAI 全站产品设计与用户体验审计

审计日期：2026-08-05（Asia/Shanghai）
审计对象：本地开发环境用户端、管理员端、桌面端、移动端、亮暗主题与中英文状态
审计目标：判断系统是否达到正式上线的成熟产品标准，并给出可执行的整体改造路线

## 1. 执行摘要

### 1.1 总体结论

当前系统已经具备较完整的业务骨架、真实 API 链路和运营能力，但**尚未达到成熟 AI 创作产品的上线体验标准**。用户感受到的“平淡、方正、像管理后台”并不是单纯的颜色或圆角问题，而是以下四个根因共同造成的：

1. **核心默认路径不可信**：图片和音乐仍会优先依赖默认 Mock Provider；视频界面虽尝试选择可运营 Provider，但服务端目录默认值仍固定为 Mock。用户首次进入创作页时可能看到不可用模型、禁用按钮或技术性错误。
2. **真实内容没有成为界面主角**：首页完成度较高，但任务、社区、灵感、个人主页、历史等页面仍以横幅、表单、指标卡和文字行为主；真实图片、视频关键帧、音频波形和生成结果没有承担视觉层级。
3. **产品语言分裂**：首页、三类内容页、四个工作台、资产与生成中心、个人/积分/API 页面像来自多套产品；管理端组件与用户端组件又交叉复用，造成“创作产品退回后台”的观感。
4. **前端样式缺少所有权边界**：全局样式超过 2.4 万行，同一页面被多个后置 CSS 文件继续覆盖。此前出现亮暗模式不一致、单页修复影响其他页、分隔线贴内容等问题，都是该结构的直接结果。

因此，下一阶段不应继续逐页“补装饰”，也不应通过全站渐变、发光和大圆角制造 AI 感。正确方向是：

- 用户端采用**内容优先的 AI 创作工具语言**：真实产物提供色彩，界面使用克制中性色、低边框、零装饰阴影、小圆角和明确的生成反馈。
- 管理端采用**高密度运营工具语言**：强调扫描效率、主从结构、批量操作和异常优先，不追求创作端的电影感。
- 两端共享字体、状态语义、交互反馈和基础控件，但使用不同的信息密度与页面模板。

### 1.2 上线判断

设计与用户体验维度当前结论：**No-Go**。

解除设计体验 No-Go 至少需要完成：

- 修复创作页默认选择不可用或 Mock Provider 的路径。
- 移除生产可见 Mock/演示内容，并建立空状态或示例内容的明确标识。
- 补全真实价格、计费周期和权益边界，删除未经业务确认的“不限量”承诺。
- 清除管理员普通导航 Toast、账户菜单跨路由残留等全局交互 Bug。
- 完成用户端统一 Shell、页面模板、创作工作台和内容展示规则的第一阶段改造。

上游已经承担的输出安全分类和真实媒体扫描不在本轮重复建设范围内；本轮只审计其用户可见状态是否清晰。

## 2. 审计范围与方法

### 2.1 覆盖范围

用户端覆盖：首页、任务广场、社区、灵感库、图片/视频/音乐/对话工作台、生成任务、资产库、API 访问、发布任务、我的任务、个人主页、积分、定价和支持中心。

管理员端覆盖 23 个分区：

- 运营：概览、可观测性、通知、支持
- 内容：任务审核、交付物、社区、灵感库、标签
- 安全：信任与安全、安全、审计日志
- 平台：系统设置、权限、用户、AI 配置、发布控制
- 财务：账务、对账、生成历史

状态覆盖：桌面端、390px 移动端、亮暗主题、中英文切换、刷新恢复、跨页面导航、空状态、失败状态和真实历史数据。

### 2.2 方法

- 使用普通用户和管理员身份完成真实浏览器走查。
- 检查首屏信息层级、主要任务完成路径、反馈、空状态、错误恢复和数据可信度。
- 检查移动端横向溢出、页面长度、辅助面板默认状态和触控操作。
- 对前端路由、状态、Provider 选择、Toast、样式导入顺序和 Mock 数据来源进行代码复核。

## 4. 用户端逐模块审计

### 4.1 首页

首页是当前完成度最高的用户页面，桌面与移动端均无明显横向溢出，媒体内容也已经出现。但它与后续页面脱节：首页像创作产品，进入任务、个人、积分或 API 后又变成通用 SaaS。

改造重点：

- 删除功能重复的入口，首屏只保留“继续创作、最近产物、推荐能力”。
- 使用当前用户真实生成结果或明确标记的授权案例，不使用匿名 Stock 图冒充生成结果。
- 保持首页视觉语言，并让 Studio、Assets、Generations 延续相同媒体比例和排版节奏。

### 4.2 任务、社区、灵感

三个页面当前共享相似大横幅，仅通过红、黄、绿色点缀区分。横幅占据大量首屏，却没有展示真正的任务、作品或方法；灵感页还出现测试标题和纯文字列表。

目标结构：

- Task：筛选工具条 + 高质量任务列表，首屏直接显示预算、交付形式、截止日期和匹配度。
- Community：作品/讨论混合流，图片或视频帧先于文字，排序只保留一个入口。
- Inspiration：不再是文章目录，改成可视化方法库；每个条目展示输入、结果、适用场景和“一键带入工作台”。

### 4.3 AI 工作台

图片、视频、音乐应采用同一 Studio 骨架，而不是共用 Hero 后各自重新发明表单。对话属于不同交互形态，但应共享模型选择、额度提示、历史与错误恢复规则。

统一 Studio 建议：

1. 顶部：工作台名称、模型选择、额度与任务状态，不放大幅营销 Hero。
2. 左侧：提示词、输入素材、必要参数；高级参数默认折叠。
3. 右侧：固定比例结果画布、生成阶段、错误恢复和产物操作。
4. 底部或结果旁：历史只显示最近 4-6 项，完整历史进入 Generations。
5. 移动端：创作/结果分段控制；提交后切到结果，失败后聚焦唯一恢复动作。

### 4.4 Generations 与 Assets

这两个页面经过局部重构，当前稳定性优于其他内容页，但仍需纳入统一 Library 模板：相同标题高度、筛选工具条、媒体比例、详情抽屉、按钮层级和分隔线规则。

Generations 的主对象应是“结果与状态”，而不是 Provider 元数据；Assets 的主对象应是可复用媒体，而不是文件治理字段。技术证据保留在详情区。

### 4.5 定价、积分、API、支持

- Pricing：先解决真实价格和权益承诺，再做视觉重构；这是交易页，不应使用占位数据。
- Points：统一 Points、Creative Credit 和 Quota 的概念，用户只需理解“现在能做什么”和“为什么发生变化”。
- API：从后台表单改为开发者任务流，提供密钥状态、快速调用、用量和 Webhook 独立视图。
- Support：结构完整，但应降低六个入口的等权竞争，并统一本地化时效文案。

## 5. 管理端审计

管理端不需要像创作端一样“更有 AI 感”，它需要更快、更稳、更容易扫描。当前最大问题是页面过长、控件过多、导航反馈噪声和缺少主从关系。

实测密度示例：

- Task review：66 个可见按钮、27 个表单控件。
- Trust & Safety：62 个按钮、32 个表单控件，页面约 2,613px。
- Users：73 个按钮、15 个表单控件，页面约 2,051px。
- AI config：61 个按钮，桌面约 7,253px，移动端约 11,540px。
- Generations：74 个按钮、23 个表单控件，页面约 3,026px。

建议架构：

- 左侧二级导航替代 23 个顶部 Chip；移动端使用分区选择器，不加载整个长页。
- 列表页使用“筛选/表格/详情抽屉”结构；选中对象后才显示操作表单。
- Provider、模型、版本、部署、路由分别成为独立资源视图，通过面包屑建立关系。
- 高风险变更统一使用“预览影响 -> 填写原因 -> 确认执行 -> 查看审计记录”。
- 导航、展开、筛选不发 Toast；保存成功可使用行内状态，跨页完成或失败才使用 Toast。

## 6. 设计系统与前端架构问题

### 6.1 当前风险

当前 CSS 规模：

- `src/index.css`：16,602 行
- `src/product-system.css`：2,689 行
- `src/workspace-workbench.css`：1,505 行
- 加上页面级样式后，主样式总量约 24,427 行

`src/main.tsx:3-13` 连续加载 11 个样式入口，`src/App.tsx:3` 又重复导入 `index.css`。Assets、Generations 等页面同时受到全局、产品系统、动效和页面文件覆盖。该结构带来：

- 选择器优先级与导入顺序决定最终外观。
- 修复某个主题或页面时容易影响另一个页面。
- 组件无法确认自己的视觉所有权。
- 设计 Token 与临时补丁混在一起，难以做全站一致性验收。

### 6.2 目标架构

1. `tokens.css`：颜色、字体、间距、圆角、状态和动效 Token。
2. `base.css`：Reset、排版、焦点、表单和无障碍基础规则。
3. `components/`：Button、IconButton、Tabs、Toast、EmptyState、MediaCard、Drawer 等组件级样式。
4. `layouts/`：UserShell、AdminShell、StudioLayout、LibraryLayout。
5. `features/`：页面只保留特有布局，不覆盖全局组件。
6. 使用 CSS Layers 或 CSS Modules 固定层级；禁止通过后置全局选择器修补单页。

迁移期间要先建立视觉回归截图，再逐模块删除旧规则，不能一次性重写全部 CSS。

## 7. 统一视觉方向

### 7.1 用户端：内容优先的 AI 创作产品

方向参考 Runway 的核心原则，但不复制品牌：

- AI 图片、视频、波形和对话结果是主要视觉资产。
- 界面使用中性色，色彩主要来自真实作品和状态。
- 常规卡片半径 6-8px，不使用大面积胶囊和装饰阴影。
- 避免渐变背景、发光球体和无意义粒子；动效服务于生成、切换和媒体预览。
- 页面可以在亮暗主题间切换，但两种主题使用同一信息层级和组件结构。
- “AI 感”来自输入被理解、生成过程可见、结果可操作，而不是紫色和 Glow。

### 7.2 管理端：运营效率优先

- 桌面优先，使用稳定左侧导航、紧凑工具条和列表-详情模式。
- 只在异常、审核和风险上使用强状态色。
- 表单字段按业务任务分组，不直接平铺数据库字段。
- 移动端只支持查看、批准/拒绝等关键任务；复杂配置明确建议桌面完成。

### 7.3 内容规则

- 不展示无法证明来源的播放量、评分、收入或案例数据。
- 示例内容必须标记来源、授权和“示例”状态，不能混入用户资产。
- 空状态不伪造内容，应解释原因并提供唯一下一步。
- 中文产品文案使用中文产品术语，Provider、Reason Code 等只出现在技术详情。

## 8. 分阶段实施路线图

### 阶段 0：解除可信度与默认路径阻断（2-4 个工作日）

- 建立按 workspace 选择首个可运营 Provider 的统一解析器；生产禁止自动选择 Mock。
- 将定价数据改为后端/配置驱动，并由业务负责人确认价格和权益。
- 删除生产构建对 `mockData.ts` 的依赖，替换为真实 API、明确示例或空状态。
- 删除管理导航 Toast；修复账户菜单跨路由、主题、语言残留。
- 为以上问题补充 E2E 回归测试。

### 阶段 1：建立设计基础与核心创作路径（5-8 个工作日）

- 建立 Token、基础组件、UserShell/AdminShell 和页面模板。

## 9. 验收指标

### 功能与默认路径

- 当任一真实 Provider 可用时，四类工作台首次进入不得默认选择 Mock 或显示禁用主按钮。
- 生产页面不得出现 `Mock Creative Provider`、E2E 标题、测试文件名或未标记示例数据。
- Pricing 的每个可购买套餐都必须有真实价格、周期、权益和限制。

### 交互

- 普通页面导航不产生 Toast；Toast 同时最多 2 条，不遮挡全局导航和主操作。
- 所有菜单支持路由变化、点击外部和 Esc 关闭。
- 移动端进入 Chat 时历史和上下文默认关闭。
- 每个页面只有一个 H1，每个空状态只有一个主动作。

### 视觉与响应式

- 390px、768px、1280px、1440px 无横向溢出、文本遮挡或操作按钮被截断。
- 亮暗主题的结构、间距和组件状态完全一致；主题只改变 Token。
- 真实媒体在 Home、Discover、Studio、Library 和 Profile 首屏承担主要视觉层级。
- 普通功能卡片圆角不超过 8px，页面分区不使用浮动卡片化包装。

### 前端质量

- 每个功能页面只有一个明确的样式所有者；不再通过 `product-system.css` 后置覆盖页面文件。
- 为 Provider 默认选择、导航反馈、菜单关闭、主题/语言保持和核心移动端布局建立 E2E。
- 建立主要路由的视觉回归基线，页面改动必须通过亮/暗、中/英和桌面/移动对比。
